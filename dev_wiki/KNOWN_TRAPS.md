# Known Traps & Architectural Pitfalls (`KNOWN_TRAPS.md`)

## 1. Workspace & Decompilation Traps
- **TRAP-001 — Space in `decompiled _apps/` Directory Name:**
  - *Symptom:* File-not-found errors when referencing `decompiled_apps/`.
  - *Reality:* The directory on disk is named `decompiled _apps/` (with a literal space before `_apps`). Always quote paths in PowerShell/CLI commands.
- **TRAP-002 — `LUTGenerator.exe.c` Contains Only CLR Metadata + `_CorExeMain()` & `LUTLibrary.dll` Is External:**
  - *Symptom:* Searching `decompiled _apps/LUTGenerator.exe.c` for C# methods or float math returns only PE/CLI metadata structs and `void entry(void) { _CorExeMain(); }`.
  - *Reality:* `LUTGenerator.exe` (`22,528` bytes, single `BSJB` header at offset `3296`) is a .NET 4.0 WPF assembly (`LUTFinder.MainWindow` / `LUTGenerator.SubWindow`) that references an external `LUTLibrary.dll` (not present on disk or embedded in `.rsrc`). Its exact pipeline (`LUTReader::Read`, `getMaxDeltaX`, `LUTCalculator::.ctor`, `getDeltaXRaw`, `getDeltaX`, `getRealForce`, `getLut2`, `Math.Round(..., 3)`) was reconstructed from `LUTGenerator.exe`'s CIL bytecode (`0x06000008` & `0x0600000E`).
- **TRAP-003 — Missing Unsymbolized MFC/Thread Functions in `DIView.exe.c`:**
  - *Symptom:* Functions referenced only via MFC message maps (`0x00401EF0` `OnDeadzone`, `0x004020E0` `OnCalibrate`, `0x00402250` `OnSaturation`, `0x0040B440` `CCalibrateDlg`) or `CreateThread`/`EnumObjects` callbacks (`0x00404C20`, `0x00404DC0`) were omitted by Ghidra's C export in `DIView.exe.c`.
  - *Reality:* Their exact machine code was audited directly from `DIView.exe` `.text` and documented in `docs/FASE_1_DESCOBERTAS_REAIS.md`.
- **TRAP-004 — Non-Interactive Subprocess `PATH` for Cargo (`%USERPROFILE%\.cargo\bin`):**
  - *Symptom:* Running `subprocess.run(["cargo", ...])` in Python fails with `FileNotFoundError: [WinError 2]` if the parent shell was started before `rustup` updated the user Registry `PATH`.
  - *Fix:* `run_regression_tests.py` explicitly resolves `Path.home() / ".cargo" / "bin"` and prepends it to the subprocess `PATH`.

## 2. DirectInput8 (`dinput8.dll`) Binary & COM Traps
- **TRAP-005 — `DIPROP_CALIBRATIONMODE` is `10` (`0x0A`), NOT `2` (`0x02`):**
  - *Symptom:* Calling `SetProperty(2, ...)` fails to switch between Raw and Cooked modes (it modifies `DIPROP_AXISMODE` instead).
  - *Fix:* Always use `MAKEDIPROP(10)` (`0x0A`) for `DIPROP_CALIBRATIONMODE` (`0` = Cooked, `1` = Raw) and `MAKEDIPROP(11)` (`0x0B`) for `DIPROP_CALIBRATION`.
- **TRAP-006 — `sizeof(DIPROPHEADER)` is `16` (`0x10`) and `sizeof(DIPROPCAL)` is `28` (`0x1C`), NOT `12` and `24`:**
  - *Symptom:* `IDirectInputDevice8::SetProperty(DIPROP_CALIBRATION, ...)` returns `DIERR_INVALIDPARAM` (`0x80070057`).
  - *Fix:* `DIPROPHEADER` has 4 `u32` fields (`dwSize`, `dwHeaderSize = 16`, `dwObj`, `dwHow`). `DIPROPCAL` is `16 + 12 = 28` (`0x1C`) bytes (`dwHow = DIPH_BYID = 2`, `dwObj = didoi.dwType`).
- **TRAP-007 — `DIView.exe` Persists Calibration via `SetProperty(DIPROP_CALIBRATION)`, Not Direct `RegSetValueEx`:**
  - *Reality:* `DIView.exe` does not import `advapi32.dll`. Calling `IDirectInputDevice8::SetProperty(DIPROP_CALIBRATION /* 0x0B */, &dipropcal)` causes `dinput8.dll` itself to write the 12-byte `REG_BINARY` `[lMin, lCenter, lMax]` into `HKCU\System\CurrentControlSet\Control\MediaProperties\PrivateProperties\DirectInput\VID_%04X&PID_%04X\Calibration\0\Type\Axes\%d` AND reloads live calibration immediately.
- **TRAP-008 — 64-Bit vs 32-Bit `DIDATAFORMAT`, `DIOBJECTDATAFORMAT` & `DIEFFECT` Struct Sizes:**
  - *Symptom:* Hardcoding 32-bit sizes (`dwSize = 24` for `DIDATAFORMAT`, `dwSize = 56` for `DIEFFECT`) causes `SetDataFormat` or `CreateEffect` to return `DIERR_INVALIDPARAM` on 64-bit (`x86_64-pc-windows-msvc`) builds because pointer fields (`rgodf`, `rgdwAxes`, `rglDirection`, `lpEnvelope`, `lpvTypeSpecificParams`) are 8 bytes wide (`sizeof(DiDataFormat) == 32`, `sizeof(DiObjectDataFormat) == 24`, `sizeof(DiEffect) == 80`).
  - *Fix:* Always compute `dw_size = size_of::<Self>() as u32` dynamically and verify 64-bit field offsets (`cb_type_specific_params` at offset `56`, `lpv_type_specific_params` at offset `64`, `dw_start_delay` at offset `72`).
- **TRAP-009 — `DISCL_EXCLUSIVE` Requires a Valid Non-Null `HWND`:**
  - *Symptom:* Passing `HWND(0)` (`ptr::null_mut()`) to `IDirectInputDevice8W::SetCooperativeLevel` with `DISCL_EXCLUSIVE | DISCL_BACKGROUND` (`0x09`) fails with `E_HANDLE` / `DIERR_INVALIDPARAM` (`NULL` `HWND` is only permitted for `DISCL_NONEXCLUSIVE | DISCL_BACKGROUND`).
  - *Fix:* `FfbWindowGuard` in `ffb_engine.rs` creates a hidden dummy Win32 `STATIC` window via `CreateWindowExW` (falling back to `GetConsoleWindow()` / `GetForegroundWindow()` / `GetDesktopWindow()`) and destroys it on `Drop`.

## 3. WheelCheck & LUT Math Traps
- **TRAP-010 — `log2.csv` Columns `startX`, `endX`, `deltaX` Are `i32` (`[-10000, +10000]`), Not Floats (`[-1.0, +1.0]`):**
  - *Reality:* `WheelCheck.exe` (`FUN_004078c0`, line 5059) writes `"%d, %d, %d, %d, %f\n"`. Only `deltaXDeg` (5th column) is floating-point; `force`, `startX`, `endX`, and `deltaX` are integers. Furthermore, row 0 is hardcoded as `"0, 0, 0, 0, 0\n"` (line 4993).
- **TRAP-011 — `deltaXDeg` Must Be Computed from Unquantized Logical Raw Units (`lMax - lMin`) & DirectInput8 Force Polarity:**
  - *Reality:* `WheelCheck.exe` sets `DIPROP_RANGE` equal to `DIPROP_LOGICALRANGE` (`[lMin, lMax]`), sets `DAT_0045be38 = +1` (line 4965: `(-(uint)(1) & 2) - 1 == +1`), applies **positive** `DICONSTANTFORCE.lMagnitude = +force` during State 4 (line 5048), which in DirectInput8 (`DIEFF_CARTESIAN` with `rglDirection[0] = 1`) rotates the wheel toward `lMin` (`0`, left) so `rawEndX < rawStartX`, and computes `deltaXDeg = dir * (MaxAngleDeg / (lMax - lMin)) * -(rawEndX - rawStartX)` (line 5057), producing positive `deltaX` (`-(endX - startX)`) and `deltaXDeg` in `log2.csv` without 16-bit quantization loss.
- **TRAP-012 — Asymmetric Moving-Average Window Smears the Deadzone Knee and Distorts Linear LUTs:**
  - *Symptom:* Applying a naive truncated moving average across index `dz_idx` (the deadzone knee) averages zero-movement deadzone points into active points, destroying both the deadzone preload jump at `lut[1]` and the identity invariant (`y == x`) near the endpoints `0.0` and `1.0`.
  - *Fix:* In `lut_math.rs` (`generate_inverse_lut`), keep `[0..=dz_idx]` strictly at `0.0`, and for each active interior point `i` in `(dz_idx + 1)..(n - 1)`, use a symmetric window radius `r = (window / 2).min(i - dz_idx).min((n - 1) - i)`. A symmetric window `[i - r ..= i + r]` preserves linear functions identically (`y == x`) while keeping `y_smooth[dz_idx] == 0.0` sharp.
- **TRAP-013 — Logitech G29/G920 Unsigned Range `[0, 65535]` Center (`32768`), `rglDirection[0] = 1`, and PID Error Sign (`posX - targetX`):**
  - *Symptom:* On a real Logitech G920 (`046D:C262`, `LogicalRange = [0, 65535]`, where `0` is $-450^\circ$ full left lock, `32768` is $0^\circ$ physical center, and `65535` is $+450^\circ$ full right lock), `step-log2` violently slammed the wheel into the mechanical end-stop, backed off slightly during the 300ms motor-off settle, and slammed into the end-stop repeatedly.
  - *Root Causes:*
    1. In DirectInput8 `GUID_ConstantForce` (`DIEFF_CARTESIAN` with `rglDirection[0] = 1`), `+lMagnitude` pulls toward `lMin` (`0`, left) and `-lMagnitude` pulls toward `lMax` (`65535`, right). Therefore, in `WheelCheck.exe` (`FUN_00404040` line `3108`), the PID error is `iVar2 = param_3 - param_2 = posX - targetX` (NOT `targetX - posX`). Writing `targetX - posX` inverts the feedback loop into **positive feedback**, driving the wheel at 100% torque straight into the mechanical end-stop!
    2. `DIEFFECT.rglDirection[0]` in `DIEFF_CARTESIAN` mode must be `1` (`+1` along the X axis, `WheelCheck.exe` lines `2826` & `5903`), not `0` (degenerate zero direction vector), and `SetParameters` must preserve the `use_object_ids` flag (`DIEFF_OBJECTIDS` vs `DIEFF_OBJECTOFFSETS`) used during `CreateEffect`.
    3. Unclamped `Kp = 5.0` without proper `1000 Hz` derivative damping (`Td = 0.9`, `Kd = 0.25`) saturates rapidly.
  - *Fix:* In `ffb_engine.rs`, `PidCenteringController::update` computes `err = pos_x_norm - target_x_norm` (with `raw = 32768` normalized to `0`), runs at true `1000 Hz` (`DEFAULT_MAX_CENTERING_FORCE = 10_000`, matching `WheelCheck.exe` `FUN_00404230` line `3188` for fast `~550 ms` centering and derivative braking), enforces an `85%` soft-lock safety envelope in State 4 (`ENDSTOP_SAFETY_LIMIT_NORM = 8_500`, $\pm 382.5^\circ$, plus `PID_HARD_SAFETY_LIMIT_NORM = 9_650` in State 2), and aborts immediately if outward runaway away from center is detected.
- **TRAP-014 — Windows `15.6 ms` Timer Quantum (`timeBeginPeriod(1)`), `Sleep(1)` `5/3 ms` (`1.68x`) `.as_millis()` Truncation Bug & Redundant `SetParameters` USB HID Calls:**
  - *Symptoms (Observed on Real Logitech G920 `046D:C262`):*
    1. 50-step `step-log2` took `~2 minutes` (`~2.4s/step`) instead of `WheelCheck.exe`'s `~58 seconds` (`~1.15s/step`).
    2. Across steps `2..40`, angular displacements (`deltaX` / `deltaXDeg`) were **`1.68x` (`~5/3`) larger** than `WheelCheck.exe` (`0.0274 deg/force` vs `0.0163 deg/force`), even though normalized curve shape matched with `R² = 0.9997`.
    3. `ENDSTOP_SAFETY_LIMIT_NORM = 5_000` (`224.5°`) caused an artificial plateau from `force = 8200..10000`.
  - *Root Causes:*
    1. Without `timeBeginPeriod(1)` (`winmm.dll`) + `SetPriorityClass` (`kernel32.dll`), Windows defaults to a `15.625 ms` (`64 Hz`) timer quantum whenever background multimedia apps are closed, collapsing the PID derivative filter (`alpha = (0.9 * 0.001) / 0.0156 = 0.057` instead of `0.90`). Furthermore, capping PID centering torque at `2800` with a `120 ms` ramp stalled return-to-center to `~1.4s/step`.
    2. Even WITH `timeBeginPeriod(1)` active, Win32 `Sleep(1)` (`thread::sleep(Duration::from_millis(1))`) sleeps across two `1 ms` kernel clock edges, averaging **`1.667 ms` (`5/3 ms`, or `~1.680 ms` including `Poll` + `GetDeviceState`)** per tick (`300` calls = `500.2–504 ms`). Calling `Duration::as_millis()` truncated `1.680 ms` down to integer `1 ms` and immediately reset `self.last_tick = now`, **permanently discarding `0.680 ms` (`40.5%` of real time) on every single tick**! Consequently, `State 4` (`state_elapsed_ms >= 300`) kept motor torque energized for **`300 * 1.68 ms = 504 ms` instead of `300 ms`**, inflating terminal-velocity angular displacement by **`504 / 300 = 1.68x` (`5/3`)** (and also stretching `State 3` settle from `300 ms` to `504 ms`)! By contrast, `WheelCheck.exe` (`FUN_004078c0` line `4975`) subtracts wall-clock timestamps (`local_2e8 = timeGetTime() - _DAT_0045be30`).
    3. Calling `IDirectInputEffect::SetParameters` on every tick even when `force` had not changed flooded the USB HID bus with ~600 redundant packets per step (whereas `WheelCheck.exe` line `5944` checks `local_148 != DAT_0045bd0c` and only sends `SetParameters(..., DIEP_TYPESPECIFICPARAMS)` when force changes, after a single `Start(INFINITE, 0)`).
  - *Fix:* `HighResTimerGuard` in `ffb_engine.rs` activates `timeBeginPeriod(1)`, `SetPriorityClass`, `SetThreadAffinityMask(1)`, and `CREATE_WAITABLE_TIMER_HIGH_RESOLUTION` (`~1.02 ms/tick = ~1000 Hz`) with RAII `Drop` cleanup; `FfbHardwareBackend::step_tick(&mut self) -> Duration` and `run_step_log2_with_backend` accumulate exact nanosecond `Duration` without integer `.as_millis()` truncation; `FfbSession::apply_force` deduplicates unchanged force commands via `last_applied_force: Option<i32>`; and `ENDSTOP_SAFETY_LIMIT_NORM` is set to `8_500` (`~382.5°`).

## 4. Native GUI (`eframe` / `egui` / `egui_plot`) & Multi-Threading Traps
- **TRAP-015 — `mpsc` Queue Blocking During `1000 Hz` FFB Runs & Non-Exclusive vs. Exclusive DirectInput8 Handle Handoff (`worker.rs`):**
  - *Symptom 1:* Sending `GuiCommand::EmergencyStopFfb` (`Key::Space` / `Key::Escape` / red emergency header button) exclusively over an `mpsc::Sender<GuiCommand>` channel fails to stop the motor immediately while the worker thread is executing the ~58-second synchronous `1000 Hz` `run_step_log2_with_backend` loop.
  - *Symptom 2:* Keeping Tab 1's `DualDeviceHandle` (`pRawDevice` + `pCookedDevice` in `DISCL_NONEXCLUSIVE | DISCL_BACKGROUND`) open while Tab 2 opens `FfbSession` (`DISCL_EXCLUSIVE`) can cause `DIERR_OTHERAPPHASPRIO` / cooperative-level contention on strict USB wheel drivers.
  - *Fix:* `HardwareWorker` in `crates/speed-precise-gui/src/worker.rs` pairs `mpsc::Sender<GuiCommand>` with a shared `Arc<AtomicBool>` (`ffb_abort_flag`) checked on every `1 ms` tick of `run_step_log2_with_backend` (`< 1 ms` motor cutoff + RAII `FfbSession::drop` -> `Stop()` + `Unacquire()`), clears `ffb_abort_flag` on the UI thread *before* enqueuing `StartStepLog2` (eliminating start/abort race windows), drops `active_dual` before `FfbSession::open`, and automatically reopens `DualDeviceHandle` once `Step Log 2` finishes or aborts.
- **TRAP-016 — `rustc 1.99+` `float_literal_f32_fallback` Lint on `egui 0.29` / `egui_plot 0.29` `impl Into<f32>` Parameters:**
  - *Symptom:* Passing unsuffixed float literals (`1.0`, `2.2`, `3.8`) to `egui::Stroke::new(width, color)`, `egui_plot::Line::width(w)`, or `egui_plot::Points::radius(r)` emits `warning: falling back to f32 as the trait bound f32: From<f64> is not satisfied` (`rust-lang/rust#154024`), breaking `-D warnings` builds.
  - *Fix:* Always annotate float literals passed to `impl Into<f32>` builder methods with explicit `_f32` suffixes (`1.0_f32`, `2.2_f32`, `3.8_f32`).
- **TRAP-017 — Concurrent Multi-Thread `DirectInput8Create` + `DualDeviceHandle::open` Driver Contention During Parallel `cargo test`:**
  - *Symptom:* Running `cargo test` without `--test-threads=1` when 4+ GUI worker unit tests simultaneously spawn background threads that all call `DirectInput8Create`, `EnumDevices`, and `DualDeviceHandle::open` (`8+` concurrent `IDirectInputDevice8W` handles on the same physical USB controller) causes `dinput8.dll` / vendor HID filter drivers to deadlock.
  - *Fix:* In production, `SpeedPreciseApp` spawns strictly **one** `HardwareWorker` (`WorkerConfig::default()`, `enable_physical_dinput: true`). In parallel unit tests, dry-run/state-machine tests set `enable_physical_dinput: false` while a single dedicated worker test (`test_worker_physical_dinput_refresh_devices`) exercises physical `DirectInput8` enumeration without multi-thread driver contention.
- **TRAP-018 — `DIPROP_SATURATION` Center-Symmetry Distortion vs. Active-Low Inverted Pedals (`0..255` on Logitech G29/G920):**
  - *Symptom:* Adjusting DirectInput8's built-in `DIPROP_SATURATION` (`6`) on unilateral pedals (especially active-low inverted pedals like Logitech G920 `046D:C262`, where resting foot-off = `255` -> `cooked = 65535` and full press = `0` -> `cooked = 0`) scales symmetrically around `lCenter`, clipping both the resting end and the pressed end instead of reaching `100%` brake/throttle at `S%` physical pedal travel.
  - *Fix:* Keep driver `DIPROP_DEADZONE = 0` and `DIPROP_SATURATION = 10000`, and compute `[lMin, lCenter, lMax]` directly via `compute_smart_pedal_calibration` (`DIPROP_CALIBRATION = 0x0B`): for inverted pedals (`raw_rest = logical_max`), `lMax = round(raw_rest - (D/100)*span)`, `lMin = round(raw_rest - (S/100)*span)`, and `lCenter = floor((lMin + lMax) / 2)` (e.g. `S=40%, D=0%` on `0..255` -> `[153, 204, 255]`), while converting UI telemetry via `compute_pedal_press_percentages` so `0%` is always bottom (foot off) and `100%` is always top (full press).
- **TRAP-019 — `egui_plot 0.29` `data_aspect(1.0)` Expansion, Plain Mouse-Wheel Scroll vs. Zoom & Post-Render Drag Jitter:**
  - *Symptom 1:* Setting `.data_aspect(1.0)` on a rectangular `egui_plot::Plot` (`width > height`) causes `PlotTransform::set_aspect_by_expanding` to force X bounds outside `[0.0, 1.0]` (e.g. `[-0.6, +1.6]`) on every frame *after* `PlotUi::set_plot_bounds` runs.
  - *Symptom 2:* By default in `egui_plot 0.29`, plain mouse wheel (`smooth_scroll_delta`) pans vertically instead of zooming unless `Ctrl` is held, and built-in `allow_drag(true)` mutates `mem.transform` *after* `bounds_modifications`, causing 1-frame rubber-banding outside `[0.0, 1.0]`.
  - *Fix:* Disable post-render unbounded navigation (`allow_drag(false)`, `allow_zoom(false)`, `allow_scroll(false)`, `allow_boxed_zoom(false)`, `set_margin_fraction(Vec2::ZERO)`), omit `data_aspect(1.0)`, handle both plain mouse-wheel and `zoom_delta` cursor-centered zooming plus left-drag panning inside `plot.show`, and enforce `clamp_unit_square_bounds` (`[0.0, 1.0] × [0.0, 1.0]`, span `0.05..=1.0`) via `plot_ui.set_plot_bounds(...)` prior to rendering every frame.
- **TRAP-020 — `dinput8.dll` Post-`SetProperty` Cooked State Buffer Reset to `32767` (`50.0%`) Until Next USB HID Report:**
  - *Symptom:* On physical DirectInput8 controllers (verified live on Logitech G920 `046D:C262`), changing pedal Saturation (`Curso Máximo`) or Deadzone (`Zona Morta Inicial`) caused the wide calibrated Output column (`p_cooked_device`) to jump to and stay locked at **`50%` (`cooked_value = 32767` out of `0..65535`)**, even while `p_raw_device` continued reporting the true physical pedal position (`255 = 0%`).
  - *Root Cause:* Calling `IDirectInputDevice8W::SetProperty` (`DIPROP_CALIBRATION = 0x0B`, `DIPROP_DEADZONE = 0x05`, or `DIPROP_SATURATION = 0x06`) invalidates `dinput8.dll`'s internal cooked axis state buffer for `p_cooked_device`, resetting `GetDeviceState` to the midpoint `(output_min + output_max) / 2 = 32767` (`50.0%`) until the USB HID driver delivers a fresh hardware interrupt packet (i.e. physical pedal movement).
  - *Fix:* In `DualDeviceHandle::apply_live_calibration` (`device.rs`), `Unacquire()` `p_cooked_device` before `SetProperty(0x0B)`, skip redundant `DIPROP_DEADZONE`/`DIPROP_SATURATION` writes when unchanged (matching `DIView.exe` `OnCalibrate @ 0x00402180`), re-`Acquire()` + `Poll()`, and evaluate `cooked_percent`/`cooked_value` via `evaluate_calibrated_output_pct` (`calibration.rs`) from `raw_value` + `axis.calibration` while `p_cooked_device` sits on the synthetic `32767` reset value; in `app.rs`, `compute_live_pedal_display_percentages` evaluates `evaluate_calibrated_output_pct` live during slider adjustments and whenever `snap.cooked_percent` diverges from the active calibration curve.
- **TRAP-021 — `egui 0.29` Default Font (`Ubuntu-Light.ttf` + `NotoEmoji-Regular.ttf`) Missing Glyphs (`U+25CF`, `U+2713`, `U+27F3`) & Emoji Baseline Drift:**
  - *Symptom:* Status bar indicator `"●"` (`U+25CF`), `"✓"` (`U+2713`), and `"⟳"` (`U+27F3`) rendered as broken missing-glyph tofu boxes (`□`), while symbols/emojis like `"⚠"`, `"▶"`, `"⛔"`, `"💾"`, `"📂"`, `"🔍"`, and `"🚀"` fell back to monochrome `NotoEmoji-Regular.ttf` with mismatched baseline height and stroke weight.
  - *Root Cause:* Direct inspection of `epaint_default_fonts`'s TrueType `cmap` tables proves `U+25CF`, `U+2713`, and `U+27F3` do not exist in **either** `Ubuntu-Light.ttf` or `NotoEmoji-Regular.ttf`.
  - *Fix:* Never use Unicode geometric dingbats or emoji codepoints for UI icons in `speed-precise-gui`; draw all UI icons (`paint_status_led`, `paint_warning_icon`, `VectorIcon`, `add_icon_button`) with anti-aliased `egui::Painter` vector primitives, and enforce 100% `Ubuntu-Light.ttf` `cmap` coverage in `run_regression_tests.py` (`verify_gui_font_glyph_coverage`).
- **TRAP-022 — Cargo `RUSTFLAGS` Override vs. `.cargo/config.toml` (`+crt-static`) & PE32+ Standalone Portability Audit:**
  - *Symptom:* Setting `env["RUSTFLAGS"] = "-D warnings"` in automation scripts causes Cargo to ignore `[target.x86_64-pc-windows-msvc].rustflags = ["-C", "target-feature=+crt-static"]` in `.cargo/config.toml`, silently falling back to dynamic `vcruntime140.dll` linking during test builds and invalidating Cargo's target fingerprint cache between test and packaging runs.
  - *Fix:* Preserve `-C target-feature=+crt-static` whenever `RUSTFLAGS` is set on Windows (`run_regression_tests.py` & `build_portable_release.py`), and parse the compiled release binary's PE32+ header directly to assert `Subsystem == 2` (`IMAGE_SUBSYSTEM_WINDOWS_GUI` via `#![cfg_attr(not(debug_assertions), windows_subsystem = "windows")]`) and zero `vcruntime*`/`msvcp*` imports in `IMAGE_DIRECTORY_ENTRY_IMPORT`.
